# Серверный выпуск: права, девять правок и Web Push

## Решение и состояние

Пользователь утвердил подготовку выпуска с **включённым Web Push**, чтобы затем проверить реальные iPhone и Android на серверном HTTPS-адресе. Сам сервер при подготовке не меняется. Реальная доставка пока не принята. Кадровые подмены остаются открытой задачей: место — объект → «Команда», Киреевой и Лазутиной новые права не выдавать.

Ветка подготовки: `codex/release-customer-workflows-20261118`. Релизный SHA — коммит этой ветки; при будущем merge фиксировать итоговый SHA отдельно. Точка перед девятью правками: `f4fa23a`, **не универсальный production rollback**.

На момент fetch `origin/main` — `986a5a1`. Текущая история содержит все её коммиты и шесть накопленных коммитов сверху: `6c02501`, `ec3e435`, `42e5b7c`, `f0f1137`, `f5524c5`, `f4fa23a`. Поэтому это выпуск **всего накопленного ACL-контура вместе с новыми правками**, а не только визуальное исправление реестра. Полная матрица прав не принята: 610 открытых критериев не считать закрытыми подготовкой релиза. Доказательства и ограничения — [локальный отчёт](product/customer-workflows-verification-2026-11-17.md).

## Что подготовлено

- Backend/frontend, зависимости и lockfile; одна общая новая аддитивная миграция девяти правок.
- Production Dockerfile теперь копирует `public`: `/push-worker.js` и локальные иконки попадут в frontend-образ. Без этого локальная проверка не гарантировала бы подключение на сервере.
- Production env-пример включает Web Push и содержит только placeholders. Локальный env остаётся выключенным.
- `scripts/prepare-web-push-env.mjs` создаёт отдельный секретный фрагмент с режимом 0600, отказывается перезаписывать существующий файл. Скрипт ничего не отправляет и не меняет runtime env.
- `scripts/check-web-push-release.mjs` использует тот же валидатор пары, что backend, и проверяет включение, production-режим, HTTPS origin и secure cookies. Не печатает ключи и не отправляет push.
- Реальный кандидат ключей подготовлен вне репозитория в закрытой папке рабочей сессии. При выкладке **сначала проверить существующие серверные ключи**: действительную пару сохранить; кандидат применять только если пары ещё нет. Не менять ключи при каждой пересборке — это потребует переподключения устройств.
- `.env.production` и его секретные варианты исключены из Git; временные preview-сборки исключены из Docker context.

## До изменений на сервере

1. Проверить фактический проект/путь/env/compose overrides через известный пользователю SSH alias `srm`; не предполагать их по старым документам. Сверить текущие SHA, image IDs, health, миграции, память и место. Посторонние проекты не менять.
2. Зафиксировать релизный SHA и прохождение применимых CI-проверок. Старые успешные доказательства не заменяют результат CI нового SHA. Не отключать проверки ради merge.
3. Подтвердить canonical domain. Шаблон и локальная сборка используют `socrm-ru-ru.ru`, но это не подтверждение текущей серверной конфигурации. Должны совпасть `APP_DOMAIN`, `APP_BASE_URL=https://<домен>`, cookie domain и build-time `NEXT_PUBLIC_API_URL=https://<домен>/api/v1`. Существующие JWT/DB/MinIO секреты не заменять примерами.
4. Закрыто сохранить текущий runtime env, PostgreSQL backup и согласованную копию/снимок MinIO; проверить читаемость и восстановление копии отдельно. Сохранить прежние image IDs под отдельными тегами до build. Не использовать локальный учебный dump как резервную копию production.
5. Зафиксировать короткое окно обслуживания: остановить записи и старый backend/фоновые обработчики перед окончательной копией и миграцией. Не выполнять seed, reset или `migrate dev`.

## Миграции

Относительно `origin/main` в пакете присутствуют:

1. `20261106100000_access_control` — накопленный контур персональных прав и аудита.
2. `20261117090000_customer_workflow_updates` — ручное членство чатов, режим/выезды мытья окон, ключ повторного расхода, таблицы подписок и очереди Web Push.

Это список различий Git, **не утверждение о pending миграциях реального сервера**. На сервере сверить `_prisma_migrations` штатным `migrate status`; применять только фактически pending через tools-сервис `migrate`. Новая миграция локально прошла, на production копии не запускалась. ALTER/индексы/FK могут блокировать записи, поэтому сначала оценить их на восстановленной копии и фактических объёмах.

## Включение и запуск

Команды ниже выполняются только в проверенной серверной папке с существующим `.env.production` и необходимыми действующими overrides. Ключи не вставлять в shell-историю, PR, сообщения или build args. Обновить env через защищённый файл; после изменения сохранить режим доступа 0600. VAPID private key нужен только backend.

```sh
(
  set -eu
  docker compose --env-file .env.production -f docker-compose.prod.yml build backend
  docker compose --env-file .env.production -f docker-compose.prod.yml --profile tools build migrate
  docker compose --env-file .env.production -f docker-compose.prod.yml build frontend
  docker compose --env-file .env.production -f docker-compose.prod.yml run --rm --no-deps backend node scripts/check-web-push-release.mjs
  docker compose --env-file .env.production -f docker-compose.prod.yml --profile tools run --rm --no-deps migrate
  docker compose --env-file .env.production -f docker-compose.prod.yml up -d --no-deps --wait backend
  docker compose --env-file .env.production -f docker-compose.prod.yml up -d --no-deps --wait frontend
)
```

Требуются уже здоровые инфраструктурные сервисы и версия Compose с `--wait`; проверить это в preflight. `set -eu` останавливает последовательность при первой ошибке. Сборки выполняются последовательно, включая отдельный `migrate` из того же фиксированного checkout, чтобы не запустить старый migration image. Первый `run` — только проверка конфигурации, он не запускает приложение, миграции или отправку. Проверить миграции до старта backend. **Старт backend уже возобновляет фоновые записи и отправку**, не называть его read-only. Старые уведомления при подключении устройства не переотправляются; реальная отправка начинается для новых событий и ручного теста.

Не выводить полный `docker compose config`, `docker inspect` environment или env в публичный журнал. При ошибке preflight включение считать неготовым, даже если обычный `/health` отвечает 200.

## Проверка после старта

- HTTPS и health, стабильность контейнеров и правильные image IDs.
- `/push-worker.js`: 200, JavaScript, без HTML-страницы входа; `/manifest.webmanifest` и обе иконки 200. Проверить в браузере успешную регистрацию worker с корневой scope. Текущий worker не содержит offline cache или перехвата запросов.
- Вход, реестр объектов: видны и работают поиск, фильтры, действующие/архив; нет перекрытия toolbar.
- Чаты: доступны положенные группы; открытие управления составом не даёт чтения чужой переписки. Не менять реальных участников ради smoke.
- Склад и финансы: разрешённое чтение заказа, сводки и истории без фиктивных рабочих записей. Отдельные реальные финансовые/складские записи выполнять только в согласованном тестовом ресурсе.
- На `/settings/notifications` сервер показывает доступность подключения, а не «не настроено». Вход и разрешения получателя действуют; никаких массовых grants для проверки.

## Приёмка телефонов

На каждом телефоне отдельно, из собственного профиля тестового получателя:

1. iPhone: установить CRM на экран «Домой», открыть с иконки; Android: открыть поддерживаемый браузер. Инструкции находятся в настройках CRM. Нажать «Подключить уведомления» и разрешить системный запрос.
2. Ручной тест при открытом приложении, затем при свёрнутом/закрытом. Показать реальный системный баннер; зафиксировать устройство/ОС/браузер и время. Статус приёма push-службой не равен получению телефоном.
3. Создать одно согласованное новое событие и проверить нажатие уведомления/переход. Текст обобщённый, без ФИО и сумм; переход проверяет актуальный доступ. Открытый черновик прежней вкладки сохраняется.
4. Отдельно отозвать чтение уведомлений, realtime и доступ к источнику: новые запрещённые события не должны доставляться; после возврата прав не должно быть догоняющей отправки старых. Уже принятый провайдером баннер нельзя отозвать с телефона, но он не раскрывает содержание.
5. Отключить устройство, проверить отсутствие последующей доставки; второе устройство не отключается. Отдельно проверить выход из учётной записи и новое подключение.

Результат внести отдельно от локальной матрицы: фактическая доставка и переход на двух платформах ещё не подтверждены. Подготовленный выпуск не закрывает этот пункт заранее.

## Откат

Не запускать автоматически старый backend поверх уже использованных новых данных. Он игнорирует ручные исключения участников, а создание расходов может потерять защиту новых повторных ключей. Возврат к `f4fa23a` не гарантирует сохранение доступа.

Если возникает проблема, закрыть пользовательские записи и остановить backend/worker. Сохранить диагностику и новые данные. Для изолированной проблемы push можно отключить `WEB_PUSH_ENABLED` и пересоздать backend **той же версии**, сохранив пару ключей, подписки и БД. Это не откатывает денежные/складские операции и не отзывает уже доставленные баннеры. Если весь backend требует отката — сначала подготовить совместимый вариант, учитывающий исключения чатов и повторные ключи, либо держать затронутый контур закрытым. Восстановление БД не автоматическое: требует решения о новых записях и согласованности с файлами/доставками.
