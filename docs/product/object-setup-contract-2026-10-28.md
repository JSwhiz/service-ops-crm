# Контракт реализации: создание объекта и графики — 2026-10-28

Источник — уточнения заказчика в текущей беседе и [план рабочей группы](object-creation-workgroup-2026-10-28.md). Документ определяет целевое поведение локальной реализации. Статусы выполнения ведутся в плане; наличие контракта не означает готовность кода.

## Инварианты и решения

- Уточнение 2026-10-29: в интерфейсе сезонность включена или выключена. При включении текущий летний/зимний профиль выбирается автоматически по ежегодным границам объекта; при выключении используется базовый профиль «По умолчанию». Границы не угадываются. Создание сохраняет настройки вместе с объектом.
- Условие оплаты выбирается в штатной позиции (например, «Уборщица» → «Уборка»); группы одного контура не создают дополнительные выплаты. Разные интервалы могут явно иметь разные контуры для отдельных дневной/ночной выплат.
- Уточнение 2026-10-29, OQ-149: менеджер может выбрать любое готовое активное условие своего объекта. Создание условий и изменение сумм остаются в контуре управления ставками; выбор привязки проверяется отдельной capability `selectPayConditions`.
- Первое стандартное предложение графика — 5/2 по дням недели. Для 2/2 предлагаются две чередующиеся группы со сдвигом 2; существующие назначения сохраняются при добавлении недостающей группы. Число групп не ограничено двумя.
- User, Employee, штатная позиция, график, ожидаемая смена, факт и дневная ячейка табеля различаются.
- Позиция имеет свободное имя и nullable headcount. Группа имеет имя, сдвиг цикла и явные назначения Employees с датами. Не ограничивать ротацию парой.
- Шаблоны 2/2, 3/3, 1/3 и прочие разворачиваются в явную повторяемую последовательность; фаза считается от date-only anchor в Москве и сохраняется между месяцами/годами. 5/2 по будням отличается от скользящего цикла.
- Предпросмотр на сервере принимает ограниченный интервал и не пишет ни присутствие, ни месячный контейнер, ни денежную ячейку. Дата/время ночной смены имеют явный переход в следующий день; операционная дата — начало смены.
- Базовое правило можно сохранить без anchor как шаблон; конкретные даты в этом состоянии не угадываются. Некомплектность/конфликт покрытия показываются как предупреждения. Ошибочные данные/ACL/версии отклоняются.
- Версии графиков действуют с явно заданной даты. Изменение графика не обновляет прошлые денежные факты. Старые объекты без позиции/anchor работают прежним путём.
- Начисление за выход: один подтверждённый оплачиваемый выход на Employee+Object+operationDate+контур оплаты. Контур задаётся явно уполномоченным на ставки пользователем; группа/случайный идентификатор события не создают новый контур. Для отдельных дневного и ночного контуров сумма дня складывается; несколько фактов одного контура оплату не умножают.
- Месячные и прочие существующие модели сохраняют действующие правила. Их сумму нельзя умножать на число групп/смен. Ручной дневной finalValue и его capability сохраняются.
- Новый сменный путь согласует дневной attendance-агрегат с табелем атомарно; при несовместимости со старой дневной записью требуется понятный конфликт, а не скрытое двойное начисление. Отмена/исправление сохраняет историю и автора.
- Работать с графиком и назначать человека не означает право задавать/изменять оплату. Новые ставки доступны в прежнем узком контуре управления тарифами; менеджеры могут выбирать только разрешённые готовые условия согласно существующему контракту.
- Основные/договорные сведения можно дозаполнять; сохраняются текущие инварианты идентификации и scope объекта. Контакт — существующий ObjectContact, Counterparty независим от юридического названия.
- Договорная сумма читается только четырьмя leadership-ролями, в том числе в API/audit payload. Даты договора не запускают автоматический lifecycle.
- Бюджеты зарплаты и расходников различаются. Новый план по статье не становится проведённым расходом. Для неподдерживаемых источников факт null с пояснением, а не 0.
- Коэффициент хранится без применения. Для его изменения отдельная permission, выдаваемая согласованным аккаунтам; нельзя выводить право по свободному ФИО из запроса.
- Создание допускает вложенные setup и позиции в одной транзакции с объектом. Повтор/ошибка не должны оставлять созданный объект без сообщённых пользователю частей. Файлы по действующему контракту загружаются после создания с сохранением объекта при сбое.

## Границы исполнителей и API

- BE-CORE владеет `objects/object-setup.*`, DTO setup и необходимыми точками create в ObjectsService/DTO. Готовит typed nullable сведения договора/площади/запуска/продаж/коэффициента/бюджетных строк. Endpoint `GET/PATCH /objects/:id/setup`; read выдаёт capabilities и version; patch — expectedVersion и отдельные проверяемые поля.
- BE-SCHEDULE владеет новой папкой `modules/object-scheduling`, всеми изменениями Prisma schema/новыми миграциями, своей интеграцией с attendance/timesheet. Endpoints под `/objects/:objectId/scheduling`: список позиций, запись позиции, preview, назначение/подтверждение смен по утверждённому typed контракту. Агент первым выдаёт точные DTO и создаёт файлы типов; оркестратор передаёт их FE.
- Объектные данные расширения сохраняются в отдельной `ObjectSetup` записи: objectId PK/FK, version, data Json, updatedAt; Json валидируется typed DTO и whitelist на сервере. Это дополнительная конфигурация объекта, а не замена ObjectContact/ObjectPlanningSettings или финансового ledger. Неполный PATCH сохраняет скрытые/непереданные поля и не обходит отдельные budget/rate/coefficient ACL.
- Оба BE исполнителя согласуют create hooks до изменения общей точки. ObjectsModule/app.module регистрирует ORCH; schema пишет только BE-SCHEDULE.
- FE владеет только frontend и использует существующие primitives/tokens. Предпросмотр берётся с backend. В создание можно передать setup/позиции, а редактирование остаётся в существующих разделах и маршрутах.

## Критерии приёмки

1. Создать объект с незаполненными дополнительными полями; reload сохраняет поля. Контрагент не создаётся из юридического имени.
2. 2/2 предлагает две группы со сдвигом 2; 1/3 — четыре при ежедневном покрытии; календарь не сбрасывает цикл на границе месяца.
3. Пустая численность не превращается в 0/число сотрудников. Существующий Employee выбирается явно; предложение не назначает.
4. Preview и чтение табеля не создают денежный факт. Факт считается один раз в одном контуре, разные явно заданные контуры складываются; месячный режим не удваивается.
5. Ручная корректировка и сохранённая история не меняются при правке графика/ставки; роли без права изменения ставки её не записывают через позицию/setup.
6. Проверить конкурирующие версии, retry, закрытый месяц, недоступность, подмену, несколько временных интервалов и ночную смену.
7. Не выводить ложные финансовые итоги: отсутствие ставки/численности/источника факта явно видно.
