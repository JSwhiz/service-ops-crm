## Cross-cutting acceptance rules

Apply these cases to every applicable row; record the actor, role and scope in test evidence:

- **Allow / deny / default:** verify explicit allow, explicit deny overriding role/creator/assignment/delegation, and removal of the personal override returning to the documented legacy default.
- **Scope:** test selected resource A allowed and B denied; parent/module deny blocks child grants and nested access. A global scalar capability never means every resource.
- **Current session and direct API:** after grant or revoke, use the same authenticated cookie/session without waiting for JWT expiry. Test the endpoint directly; a hidden button is not enforcement.
- **No side effects:** on every deny, assert unchanged domain rows, versions, balances/stock, history, outbox/notifications and audit except for a deliberately specified security-denial log.
- **Sensitive projections:** check nested DTOs and serialized response fields, audit/history payloads, search, exports, files, notifications and realtime for denied or secret fields.
- **Legacy compatibility:** zero overrides preserve each documented legacy outcome unless the registry records a contract-approved drift correction. Test personal deny precedence and expired/revoked assignments/delegations.
- **Independent authority and lifecycle:** initiating a change does not authorize its approval; self-approval remains denied. Closed periods, frozen/archived/closed resources, posted financial facts, immutable snapshots, idempotency and one-effect rules remain in force.
