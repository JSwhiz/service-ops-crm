## Главные принципы реализации

### 1. Не удаляем рабочие данные физически

Чаты, сообщения, фото, задачи, финансовые операции и карточки с историей не удаляются из базы физически через интерфейс.

Используем:

```text
hiddenAt
deletedAt
archivedAt
cancelledAt
```

Это нужно для истории, аудита и защиты от конфликтов.

### 2. Финансовые операции не редактируются

Если в подотчёте или оплатах ошибка, создаётся корректирующая операция.

Нельзя делать обычное редактирование финансовой записи, потому что это ломает доверие к системе.

### 3. Пользователь, сотрудник и кандидат — разные сущности

- Пользователь системы — тот, кто входит в CRM.
- Сотрудник — человек в операционном или кадровом контуре.
- Кандидат — человек из HR-воронки, который ещё не является сотрудником.

Эти сущности нельзя смешивать без явной модели.

### 4. Уведомления строятся через матрицу

Нельзя отправлять всем всё.

Нужно фиксировать:

```text
событие -> получатели -> канал доставки -> обязательность
```

### 5. Сначала фундамент, потом крупные модули

Нельзя начинать с графика, подотчёта или кандидатов, пока не стабилизированы:

- мессенджер;
- уведомления;
- задачи;
- права;
- аудит.

# Этап 1. Мессенджер foundation

## Цель

Перевести текущие чаты в нормальный внутренний мессенджер уровня Telegram-lite.

## Почему этот этап первый

Чаты уже есть в системе, но сейчас это не полноценный мессенджер.  
Если сразу делать уведомления, задачи и пересылки без нормальной модели сообщений, потом придётся переделывать.

---

## 1.1. Личные чаты

### Что делаем

Любой активный пользователь системы может создать личный чат с любым другим активным пользователем.

### Как делаем

Добавляем тип комнаты:

```text
chatRoom.roomType = direct | group | system_default
```

Для личного чата добавляем:

```text
chatRoom.directKey
```

`directKey` формируется из двух userId в отсортированном порядке.

### Правило

Если личный чат между двумя пользователями уже есть, новый не создаётся.  
Открывается существующий.

### Результат

Пользователь может написать любому сотруднику напрямую, без дублей чатов.

---

## 1.2. Групповые чаты

### Что делаем

На первом этапе не разрешаем всем пользователям создавать групповые чаты.

### Кто может создавать

Рекомендуемо:

```text
founder
deputy_founder
director
deputy_director
corporate_director
```

Или персонально согласованный список:

```text
Герасимов
Лебедев
Степанова
Горбачёва
Никитина
```

### Кто может глобально закрывать групповые чаты

Только:

```text
Герасимов
Лебедев
Степанова
```

### Как делаем

Лучший вариант — permissions:

```text
chat.group.create
chat.group.rename
chat.group.manage_participants
chat.group.delete_global
```

На быстрый первый проход можно:

- создание групп — по ролям;
- глобальное закрытие — по whitelist логинов.

---

## 1.3. Скрытие чата у пользователя

### Что делаем

Удаление чата для обычного пользователя = скрытие только у него.

### Как делаем

В участника комнаты добавляем:

```text
chatRoomParticipant.hiddenAt
chatRoomParticipant.leftAt
```

### Логика

- `hiddenAt` — пользователь скрыл чат из списка.
- `leftAt` — пользователь покинул групповой чат.
- Новое сообщение в скрытом чате может вернуть чат в список.

---

## 1.4. Глобальное закрытие чата

### Что делаем

Добавляем возможность закрыть чат глобально, но без физического удаления.

### Как делаем

В комнату добавляем:

```text
chatRoom.deletedAt
chatRoom.deletedByUserId
chatRoom.deleteReason
```

### Зачем

Чтобы сохранить историю и аудит.

---

## 1.5. Редактирование сообщений без ограничения времени

### Что делаем

Снимаем ограничение 30 минут на редактирование своего сообщения.

### Как делаем

Добавляем историю редактирования:

```text
chatMessageEditHistory
- messageId
- oldText
- newText
- editedByUserId
- editedAt
```

### UI

Показываем метку:

```text
изменено
```

---

## 1.6. Удаление сообщений

### Что делаем

Удаление сообщения = soft-delete.

### Как делаем

В сообщение добавляем:

```text
chatMessage.deletedAt
chatMessage.deletedByUserId
chatMessage.deleteMode
```

### UI

Вместо текста показываем:

```text
Сообщение удалено
```

### Важно

Вложения физически из MinIO не удаляем.

---

## 1.7. Ответ на сообщение

### Что делаем

Добавляем reply.

### Как делаем

В сообщение добавляем:

```text
chatMessage.replyToMessageId
```

API возвращает preview исходного сообщения:

- автор;
- короткий текст;
- тип вложения.

---

## 1.8. Пересылка сообщений

### Что делаем

Можно пересылать:

- текст;
- фото;
- файлы;
- текст + вложения.

### Как делаем

В сообщение добавляем:

```text
chatMessage.forwardedFromMessageId
chatMessage.forwardedFromChatRoomId
chatMessage.forwardedFromAuthorUserId
```

Файлы не загружаем повторно.  
Создаём новую attachment-связь на существующий fileId.

---

## 1.9. Реакция сердечком

### Что делаем

Один пользователь может поставить одну реакцию на одно сообщение.

### Как делаем

Создаём таблицу:

```text

- messageId
- userId
- reactionCode
- createdAt
```

Уникальный индекс:

```text
messageId + userId
```

Повторное нажатие снимает реакцию.

---

## 1.10. Поиск в чатах

### Что делаем

Делаем глобальный поиск по чатам.

### Где ищем

- сообщения;
- названия чатов;
- участники;
- ФИО;
- логины;
- телефоны сотрудников;
- объекты;
- адреса объектов;
- разовые заказы.

### UI

Результаты группами:

```text
Сообщения
Чаты
Сотрудники
Объекты
Разовые заказы
```

При клике на сообщение:

- открываем чат;
- скроллим к сообщению;
- подсвечиваем найденный фрагмент.

## Проверка этапа 1

- Пользователь создаёт личный чат.
- Дубли личных чатов не создаются.
- Групповые чаты создают только разрешённые роли.
- Обычный пользователь может скрыть чат у себя.
- Глобально закрыть чат могут только Герасимов, Лебедев, Степанова.
- Сообщение можно редактировать без ограничения времени.
- История редактирования пишется.
- Удалённое сообщение показывает “Сообщение удалено”.
- Reply работает.
- Forward работает.
- Реакция heart работает.
- Поиск находит сообщение, сотрудника и объект.

# Этап 2. Realtime и уведомления

## Цель

```text

```

---

## 2.2. Матрица уведомлений

### Что делаем

Создаём управляемую карту уведомлений.

### MVP-формат

Сначала можно хранить в коде:

```text
eventType -> recipients -> channels
```

Позже переносим в БД.

### Базовые события

| Событие                    | Получатели                                      |
| -------------------------- | ----------------------------------------------- |
| Новое личное сообщение     | получатель                                      |
| Новое сообщение в группе   | участники, кроме автора                         |
| Новая задача               | исполнители                                     |
| Изменение срока задачи     | исполнители + создатель                         |
| Задача просрочена          | исполнители + создатель                         |
| Задача ждёт подтверждения  | подтверждающий                                  |
| Новый разовый заказ        | менеджеры разовых + руководство                 |
| Изменение разового заказа  | менеджеры заказа + руководство                  |
| Изменение объекта          | ответственный + менеджеры объекта + руководство |
| Новый кандидат             | HR                                              |
| Кандидат без ответа 2 часа | менеджер + HR                                   |
| День рождения              | HR + руководство                                |

---

## 2.3. In-app toast

### Что делаем

### Как делаем

---

## 2.5. Telegram-дублирование

### Что делаем

Добавляем Telegram-бота для важных уведомлений.

### Как делаем

Пользователь привязывает Telegram через код:

```text

```

Храним:

```text

```

## Проверка этапа 2

- Toast отображается.
- Browser notification работает после разрешения.
- Telegram уведомление приходит привязанному пользователю.
- Автор события не получает лишние уведомления.
- Офлайн-пользователь не теряет важное уведомление.

# Этап 3. Новая модель задач

## Цель


## 3.2. Обязательный срок

Добавляем:

```text

```

Срок обязателен для всех задач.

## 3.3. Видимость задачи

Добавляем:

```text

```

Варианты:

```text

```

## 3.4. Таблица видимости

Для `selected_users`:

```text
taskVisibleUser
- taskId
- userId
```

## 3.5. Подтверждение задачи

Добавляем:

```text
requiresConfirmation
confirmationMode
confirmerUserId
```

Варианты:

```text
none
creator
selected_user
```

## 3.6. Статусы задач

Целевой список:

```text
new
assigned
in_progress
partially_completed
completed
awaiting_confirmation
returned_to_work
closed
cancelled
```

Просрочка не хранится как статус.  
Она вычисляется:

```text
dueAt < now && status not in closed/cancelled
```

## 3.7. Возврат закрытой задачи

Разрешаем:

```text
closed -> returned_to_work
```

Только:

- создателю;
- подтверждающему;
- руководителю с широким доступом.

Нужна причина возврата.

## 3.8. Комментарии и файлы

Добавляем позже или вторым подэтапом:

```text
taskComment
taskAttachment
```

## Проверка этапа 3

- Можно создать общую задачу.
- Можно создать личную задачу.
- Можно создать задачу по объекту.
- Можно создать задачу по разовому заказу.
- Срок обязателен.
- Просрочка считается автоматически.
- Видимость selected_users работает.
- Исполнитель всегда видит задачу.
- Подтверждение работает.
- Закрытую задачу можно вернуть.

```text
day_off
vacation
sick_leave
```

## 8.2. Заказы в календаре

Один менеджер может иметь несколько заказов в день.

```text
oneTimeOrderCalendarAssignment
- orderId
- managerUserId
- date
```

## 8.3. UI

Календарная сетка:

```text
строки — менеджеры
колонки — дни
ячейки — заказы / статусы дня / задачи
```

## 8.4. Конфликты

Если у менеджера уже есть заказ:

- не запрещаем;
- показываем предупреждение.

Если отпуск/больничный:

- требуем подтверждение руководителя.

## 8.5. Задачи в календаре

Показываем задачи, связанные с разовыми заказами:

- внутри ячейки;
- или badge “3 задачи”.

## 8.6. Excel

Экспорт за период:

```text
менеджер
дата
статус дня
заказы
количество заказов
отработанный день
комментарий
```

## Проверка этапа 8

- Открывается месяц.
- Можно переключать месяцы.
- Можно назначить заказ на дату.
- Можно назначить несколько заказов в день.
- Можно поставить отпуск/больничный.
- Показывается предупреждение о занятости.
- Можно выгрузить Excel за период.

# Этап 9. Подотчёт и оплаты

## Цель

Связать финансы сотрудников, разовые заказы и сверку.

## 9.1. Видимость

Обычный пользователь видит только свой подотчёт.  
Руководство видит всех.

## 9.2. Типы операций

```text
top_up
issue
expense
return
correction
order_payment
```

## 9.3. Операции нельзя редактировать

Если ошибка — создаётся корректировка.

## 9.4. Статусы операций

```text
pending_reconciliation
confirmed
rejected
cancelled
```

## 9.5. Фото чека

Опционально:

```text
receiptFileId
```

## 9.6. Баланс

Баланс считается из подтверждённых операций.

## 9.7. Связь с разовым заказом

Операции из разового заказа создают записи с:

```text
sourceEntityType = one_time_order
```

## Проверка этапа 9

- Пользователь видит свой подотчёт.
- Не видит чужой.
- Руководство видит всех.
- Операция ждёт сверки.
- Подтверждённая операция влияет на баланс.
- Ошибка исправляется корректировкой.
- Операция из заказа попадает в подотчёт.
