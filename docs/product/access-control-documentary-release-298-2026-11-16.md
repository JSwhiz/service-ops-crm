## Реальные препятствия выпуску

Новых подтверждённых **неисправленных текущих дефектов** эта документальная работа не установила. Это не заключение об отсутствии ошибок. Выпуск пока ограничивают следующие недоказанные safety-свойства:

1. **Excel календаря: linked Task count.** Сохранён actual-before, в котором закрытая Task попадала в счётчик XLSX. В текущем `loadAccessibleExportOrders` уже есть `taskVisibilityWhere`, поэтому старое утверждение «код по-прежнему unwrapped» неверно. Но точный successful post по **XLSX bytes** в рассмотренных материалах не установлен. Нужны две адресные фазы: tasks.read deny и tasks.access deny; A исключён, независимый B остаётся. Исправленный count в order API не заменяет этот экспорт.
2. **Прямое подтверждение складской выдачи без фото.** Для `inventory.resolve_missing_photo/K5` нужен terminal UI trace и точный direct-route результат после отмены movement/изменения существующей pending-заявки либо parent deny во время source-lock wait. Shared approvals resolver не является тем же endpoint. Само отсутствие pending-заявки у допустимого legacy movement не объявлено запрещённым: это было чрезмерным требованием старого gap.
3. **Открытые чувствительные панели и формы —45 ячеек.** Недостаёт exact DOM/terminal результата при отзыве и позднем ответе. Нужны понятный отказ/блокировка write, отсутствие старых данных при потере read и ручное восстановление без автозаписи; дополнительный серверный403 уже принятого handler не нужен.
4. **Конфликтующие и terminal операции —34 ячейки.** По каждой названы source, законный winner, затронутый domain/audit graph, допустимый ACK и реальные ограничения. Не требуются несуществующие финансовые инварианты в чате и искусственная дедупликация двух самостоятельных разрешённых операций.
5. **Вложение к ТЗ —1 ячейка.** Для `one_time_orders.specification.attachments/K3` проверять именно File/link/storage cleanup/worker эффекты данного attach, а не неизменность всех таблиц БД и всех каналов системы.
6. **207 привязок сохранённых доказательств.** До зачёта нужно связать конкретный защищённый DTO/source или late phase с текущим потребителем. Наличие общего guard, outbox или похожего sibling результата не подтверждает чужой endpoint/байты/сокет. Это доказательный барьер, а не207 новых воспроизведённых ошибок.

## Какие требования сокращены или исправлены

- Отзыв **write** не должен скрывать данные, которые всё ещё разрешено читать. Read-deny проверяется для команды только там, где чтение действительно является обязательным parent/invariant её guard.
- К1–К3, уже принятые для того же кода и контекста, не повторяются ради нового отчёта.
- В рассмотренных DTO `tasks.create` и `accountability.issue_cash` нет requestId/idempotency key. Два самостоятельных разрешённых POST не обязаны схлопываться в один. No-auto-replay и отзыв до записи остаются обязательными.
- Не добавляются отдельные экспорты, файлы, сканы, socket producers или новые workflows там, где их нет. Статическое исключение отдельного компонента не делает весь критерий Н/П.
- Не требуется сохранять draft у read-only истории. При сохранённом read после write deny нужен допустимый собственный черновик; при read-loss — закрытая карточка без её данных.
- `candidates.denied` — неманипулируемый legacy negative, не новый allow workflow. OQ157 не решён этой работой.
- Календарный шаблон текста в gaps кандидатов/Employee не принимается за same-code наблюдение их карточки.
- Сохранённые авторские whole-заявки не равны независимому разрешению зачёта. Withdrawn retry E468-v1 не восстановлен автоматически.

## Ограничения документальной работы

Просмотрены95 адресно относящихся исходников и метаданные сохранённых заявок. AST/call references являются статическими кандидатами привязки, не исполненными HTTP paths и не доказательством полного branch coverage. Отсутствие literal в17 ячейках не трактуется как Н/П: module inheritance/dynamic adapters требуют отдельной exact-привязки. Исходники и статусы приёмки не изменялись; обновляются только документы и gaps.
