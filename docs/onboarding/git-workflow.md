# Git Workflow

## Назначение

Этот документ фиксирует рабочую дисциплину Git для проекта Service Ops CRM.

Цель:

- держать историю проекта чистой;
- не ломать стабильные ветки;
- уметь безопасно откатываться;
- фиксировать стабильные checkpoints.

## Базовые ветки

### main

Стабильная ветка проекта.

В нее попадают только:

- проверенные изменения;
- стабильные checkpoint-версии;
- состояния, к которым можно безопасно вернуться.

### dev

Основная интеграционная ветка.

В ней собираются:

- завершенные feature-задачи;
- проверенные foundation-изменения;
- текущая рабочая версия до перевода в stable checkpoint.

### feature/\*

Рабочие ветки под отдельные задачи.

Примеры:

- `feature/auth-foundation`
- `feature/prisma-foundation`
- `feature/objects-module-foundation`

## Рекомендуемый рабочий цикл

1. взять актуальную `dev`
2. создать новую `feature/*` ветку
3. выполнить задачу
4. локально проверить:
   - `pnpm ci:check`
5. закоммитить изменения
6. слить в `dev`
7. после набора стабильного блока изменений перевести `dev` в `main`
8. поставить tag

## Правила по веткам

### Для main

- не делать прямые коммиты;
- не использовать как рабочую ветку;
- использовать только для стабильных состояний.

### Для dev

- не держать поломанное состояние дольше, чем это необходимо;
- не копить большие несобранные куски;
- считать ее интеграционной веткой, а не свалкой задач.

### Для feature/\*

- делать короткоживущими;
- не держать неделями;
- каждая feature-ветка должна решать один логический блок.

## Формат commit message

Рекомендуемый формат:

- `feat(auth): add login foundation`
- `fix(frontend): correct protected layout redirect`
- `chore(prisma): update generate scripts`
- `docs(workflow): add git process documentation`
- `ci(actions): add baseline workflow`

## Типы коммитов

- `feat` — новая функциональность
- `fix` — исправление ошибки
- `chore` — служебные изменения
- `docs` — документация
- `refactor` — внутренняя переработка без изменения внешнего поведения
- `ci` — pipeline / automation
- `build` — build/tooling/package changes

## Когда ставить tag

Tag ставится, когда:

- завершен логический этап;
- проект собирается;
- `pnpm ci:check` проходит;
- состояние можно считать checkpoint-версией.

## Как откатываться

### Предпочтительно

- `git revert` для точечных изменений
- возврат к tagged checkpoint
- создание ветки от стабильного тега

### Не рекомендуется

- хаотичный force push
- переписывание истории без крайней необходимости
- использование reset как основного способа командной коррекции истории

## Foundation checkpoint

После завершения этапов Week 1 foundation проект должен быть отмечен тегом:

- `v0.1.0`

Этот тег означает:

- foundation репозиторий собран;
- backend/frontend shell существуют;
- auth есть;
- prisma есть;
- ci есть;
- можно безопасно двигаться в доменные модули.
