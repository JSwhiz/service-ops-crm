# Единые окна создания и общий UI-проход

Дата: 2026-10-31. Статус: детализированный план реализации, не отчёт о готовности.

## Объём и неизменяемые условия

Запрос заказчика: формы создания открываются поверх текущей страницы по принципу существующего Dialog замещений; одновременно выполняется утверждённый проход по меню, ФИО, датам, кнопкам, таблицам и календарям.

Источники: STYLE_SOURCES.md, UI_ARCHITECTURE.md, COMPONENT_CONTRACTS.md, продуктовые контракты, текущие формы и предоставленные заказчиком скриншоты. Общая навигация и палитра сохраняются. Никаких новых обязательных бизнес-полей, ролей, расчётов, статусов, автопересчёта истории или схемы БД в этом UI-пакете.

Человеческий смысл операции важнее механического переноса всей страницы в маленькую модалку. Окно создания типа оборудования не равно созданию конкретной единицы. Кандидат и Employee не становятся User. График, назначение, факт выхода, начисление и выплата остаются разными сущностями.

## Предварительная проверка кода

- Существующий `shared/ui/overlays` уже имеет нативный modal dialog, заголовок, прокручиваемое тело, footer, busy, Escape и восстановление фокуса. Его развиваем, а не создаём второй набор окон.
- Базовый Dialog ограничен 560 px. Для реальных длинных потребителей нужны явные размеры 800/1040 px в рамках существующей UI-архитектуры. Не расширять одновременно все ConfirmDialog/ReasonDialog.
- Страница equipment/new сейчас содержит создание типа, список/удаление типов и форму единицы. Это три назначения, не одна форма.
- В календаре отсутствий toolbar состоит из растягивающейся левой колонки и правых фильтров; отдельный поиск пользователя дублирует выбор, форма отсутствия вставляется в страницу. Планируется общая панель и Dialog вместо врезки.
- Impeccable detector по 7 выбранным файлам форм вернул пустой список замечаний. Это не проверка ширины реального поля, слоя popover, zoom или пользовательского пути. Автоматический результат не считать приёмкой.

## Общий контракт окна

### Геометрия

| Класс окна | Целевой максимум | Потребители |
|---|---:|---|
| Компактное | 560 px | Размер ковра, тип оборудования, отсутствие, короткие справочники |
| Обычное | 800 px | Контрагент, номенклатура, кандидат, задача, единица оборудования |
| Расширенное | 1040 px | Объект, разовый заказ, сотрудник |

Это верхние границы, не фиксированные размеры: окно помещается в доступный viewport, на телефоне — полноэкранное. Основная сетка — одна/две колонки; не держать три узкие колонки ради экономии высоты. Колонки схлопываются по доступному месту. Контент никогда не требует горизонтального скролла окна.

Внутри окна: заголовок и крестик → для длинных форм навигация по разделам → тело формы → footer «Отмена / Создать …». Шапка и действия остаются видимыми; прокручивается тело. Учесть safe-area и экранную клавиатуру. Не добавлять вложенные прокручиваемые карточки для каждого раздела; собственный скролл допустим у длинного списка вариантов.

### Размеры полей

- ФИО/название/адрес — широкий текстовый столбец, до ширины раздела; ФИО не делить на отдельные обязательные части.
- Дата — ориентир 220–260 px, не 100% рабочего стола; время отдельным компактным контролом, если оно предусмотрено.
- Телефон — около 240–300 px; добавление второго номера отдельной строкой, удаление доступно по подписанной иконке, длинный номер не рвётся посередине.
- Сумма — около 180–240 px; количество/площадь/размер — около 120–180 px. Единица измерения указана в подписи. Не ограничивать допустимую длину числа только ради визуала.
- Выбор человека — достаточно места для ФИО и логина; варианты переносятся по словам и растут по высоте. Выбор нескольких — компактные строки выбранных людей и поиск.
- Комментарий — изначально 3–4 строки, растёт/изменяется пользователем; не большое пустое полотно. Подсказка отделена от значения и ошибки.
- Основная кнопка по содержимому на desktop; полная ширина допустима для главного действия на телефоне, не для каждого «Обновить».
- Соседние поля выровнены по верхней границе контролов; длинная подсказка под одним полем не растягивает соседний input. Не задавать обычным полям `height:100%`.

Конкретные значения проверяются с текущими шрифтами/токенами, это не новый дизайн-набор и не повод уменьшать шрифт.

### Жизненный цикл и навигация

1. Открытие из реестра/карточки/глобального «+» сохраняет фильтры, страницу, прокрутку и выбранную запись фона. Фон недоступен для ввода, пока окно открыто.
2. Существующие `/new` и query-параметры сохраняются. Прямой вход, обновление и ссылка из календаря работают; окно имеет определённый разрешённый фон даже без истории браузера. Закрытие не должно отправлять на случайный внешний сайт через слепой `back()`.
3. Перенос формы в окно не должен выполнять POST при переключении разделов или скрывать обязательные данные.
4. Для длинных форм — разделы без принудительной последовательности. Все существующие поля доступны до создания. Ошибка в другом разделе открывает его, показывает сводку и переводит фокус к полю.
5. Ввод переживает переключение разделов, поиск в справочнике и закрытие вложенного выбора. Не хранить кадровые/финансовые черновики автоматически в localStorage.
6. Крестик, Escape, отмена и навигация используют один dirty guard. При несохранённых данных — существующее подтверждение. На пустой форме закрытие без лишнего вопроса. Случайный клик по затемнению не уничтожает ввод.
7. Вложенное меню по Escape закрывается первым; следующий Escape относится к форме. Вложенное подтверждение не закрывает одновременно родителя.
8. Во время сохранения — pending, одна отправка, действия согласованы. Ошибка сохраняет ввод, даёт понятный повтор. После подтверждённого успеха не повторять мутацию из-за ошибки обновления списка.
9. При неизвестном результате таймаута нельзя обещать универсальную защиту от дублей без серверной поддержки: сохраняем имеющуюся идемпотентность; недостающую фиксируем отдельно, не меняем API незаметно.
10. После успеха — явное уведомление и предусмотренный переход/обновление реестра. После отмены — возврат фокуса на кнопку открытия.

## Формы сверху вниз

### 1. Объект — расширенное окно

Разделы: **Основное → Договор → Ответственные и контакты → Оплата и сезоны → Штат и графики → Плановые статьи → Инструкции**.

- Основное: название и внутреннее имя; адрес; контрагент из доступных ссылочных записей; существующий статус, если он доступен на создании. Не объединять юридическое название объекта с контрагентом.
- Договор: юридическое название; площадь компактно; плановый запуск; начало и окончание договора; сумма в месяц; ответственный за продажи. Пустое окончание означает отсутствие даты, не автоматическое изменение статуса.
- Ответственные: существующий допустимый User-ответственный, менеджеры отдельным множественным выбором; контакты — компактный список с редактором строки. Не подставлять Employee в выбор пользователей.
- Оплата: существующий базовый профиль и отдельные условия/контуры; сезонность выключена или автоматическое определение по сохранённым датам. При выключении условные настройки не должны незаметно потеряться; не пересчитывать историю.
- Штат: произвольное название позиции; количество мест может оставаться пустым; выбранные готовые условия объекта; группы графика, шаблоны, смещения и назначения Employee — по действующему контракту. Разворачивать редактор одной позиции, не десятки больших форм. Предпросмотр не создаёт факт/начисление.
- Плановые статьи: существующий список, сумма и периодичность; условные месяцы/число выполнений/распределение показываются по выбранной статье. Пусто не заменяется нулём. Доступ к суммам и коэффициенту не расширяется из-за нового контейнера.
- Инструкции: существующие особенности, сезонные работы и шаги. Ничего не удалять ради компактности; заполненные разделы имеют видимый индикатор.

Все настройки можно внести до создания либо дозаполнить по прежней логике после; не сводить создание объекта к трём полям вопреки ранее согласованному объёму.

### 2. Контрагент — обычное окно

Название → юридическое название → контактное лицо/телефон → комментарий. Две колонки там, где есть место, длинное название и комментарий — широкие. Обязательность по существующей форме. Связывание объектов не делать новым обязательным условием создания.

### 3. Разовый заказ — расширенное окно

Разделы **Основное → Планирование и команда → Условия → ТЗ → Заметки**.

- Название и адрес; существующий статус. Дата: без даты / один день / период; выбор включает соответствующие компактные поля.
- Связанный объект из разрешённых, контакт, телефон; менеджеры User. Контекст даты и менеджера из календаря сохраняется при открытии окна.
- Согласованная сумма и плановый способ оплаты. План не становится фактическим поступлением; не добавлять денежное действие к созданию.
- Каталог/оба шаблона/отдельные пункты и ручной состав — только руководящий круг с самого начала. Менеджеру не открывать конструктор. Состав и формулировки сохраняются снимком; конфликты расписания подтверждаются существующим способом.
- Все заметки доступны; свёрнутый заполненный раздел явно помечен. Копирование заказа использует тот же контейнер, но сохраняет существующие правила копии и прав.

### 4. Номенклатура — обычное окно

Название на ширину → категория и компактная единица измерения → примечание. Существующие значения/валидация сохраняются; не превращать свободную единицу или категорию в закрытый справочник без отдельного решения. Создаётся номенклатура, не приход и не списание остатка.

### 5. Размер ковра — компактное окно

Длина/ширина рядом, обе в сантиметрах → стоимость замены → «Добавить размер». Пустая цена отличается от нуля. Не создавать автоматически ковры на объектах и не менять сохранённую историю стоимости.

### 6. Оборудование — две отдельные операции

- **Добавить единицу**: тип из существующего каталога; инвентарный номер; серийный номер; заметки. Существующие обязательность и проверки уникальности сохраняются.
- **Создать тип**: категория; название; бренд/модель; заметки. Список и удаление типов — управление каталогом, не тело создания единицы.
- Создание типа из формы единицы доступно только при прежнем праве. Предпочтительно временная внутренняя панель с возвратом к единице, а не три окна поверх друг друга. Уже введённые номера сохраняются; созданный тип подставляется. Создание типа и единицы не выдаётся за атомарную операцию: тип может уже существовать, даже если единица не сохранена.

### 7. Задача — обычное окно, с возможностью расширенного тела

Название → описание → приоритет и требования к отчёту → существующие связи с объектом/разовым заказом → дата срока и необязательное точное время → исполнители → видимость/подтверждение и остальные текущие настройки → вложения.

Выбранные исполнители — отдельный компактный список; поиск по доступным User, без огромной сетки чекбоксов всех пользователей. Не менять правила совместимости связей, обязательность срока, требования к результату или ACL. Скрепка использует исправленный общий механизм меню.

### 8. Отсутствие — компактное/обычное окно

Пользователь, если действующее право позволяет выбрать другого; тип → начало/окончание → комментарий по действующей приватности. Из клетки календаря берутся человек/дата; из общей кнопки — текущий разрешённый контекст. При редактировании фиксированные поля остаются фиксированными. Это User-календарь, не кадровое отсутствие Employee.

### 9. Замещение — сохранить существующий образец

Кто замещает → доступные объекты с поиском и счётчиком выбранных → начало сразу/по времени → окончание по Москве → основание. Сохранить ограничения передачи прав и обязательность причины. Подтянуть общие dirty guard, поля и размещение popover; не переписывать бизнес-операцию.

### 10. Кандидат — обычное окно

ФИО на ширину → тип → телефоны → рассмотрение: объект по умолчанию и ответственные менеджеры, у каждого допустимый объект рассмотрения → комментарий. Для обычного/резервного кандидата сохранить разные требования. Выбранные менеджеры не теряются при поиске/смене представления. Назначение менеджера на рассмотрение не оформляет сотрудника и не назначает Employee на объект.

### 11. Сотрудник — расширенное окно

Разделы **Контакты → Работа → Режим → Документы и примечание**.

ФИО; телефоны; дата рождения; адрес. Далее тип сотрудника, статус, должность, базовая ставка по существующим правам. Рабочий режим: шаблон и его условное описание, время, предпочтения. Документы — существующие отметки/поля, не придуманная новая загрузка паспортов. Не создавать аккаунт CRM, назначение на объект, выход или выплату вместе с Employee без существующей операции.

### Дополнительные точки, не ограниченные присланными снимками

Инвентаризация реализации должна включить глобальный «+», добавление из связанных карточек, копию заказа, добавление записи календаря, статьи/расходы подотчёта, складские движения, новые пункты/шаблоны ТЗ и редакторы контактов/ставок/графиков. Общий внешний вид не даёт разрешения объединять разные команды API. Не переносить все редакторы карточки в модалки автоматически: текущий запрос в первую очередь про создание.

## Календарные панели

- Существующий MonthPeriodPicker сохранить. Месяц/стрелки — цельный блок; кнопки не растягиваются и не отрываются друг от друга.
- Общая нижняя линия контролов: период, выбор пользователя, тип, действие. Учесть подписи над полями; не выравнивать месяц без подписи по центру всей высоты соседних полей.
- На недостаточной ширине — предсказуемые строки: период и основное действие, ниже фильтры; на телефоне одна колонка без горизонтального скролла панели.
- Убрать дублирование поиска только при сохранении его смысла: поиск по строкам календаря и выбор одного пользователя могут быть разными режимами. Если объединяем, оба сценария должны остаться доступны.
- Первые колонки людей/объектов остаются читаемыми при скролле сетки; длинные имена раскрываются. У дней/действий доступные названия. Ни смены Employee, ни выплаты в этом проходе не пересчитываются.

## Совместное исполнение с ранее утверждённым проходом

1. Зафиксировать инвентарь форм, источники открытия, существующие обязательные поля и исходные screenshots.
2. Общие механизмы: Dialog нужных размеров, навигация длинной формы, группы полей/действий, размещение меню, вывод ФИО/дат и dirty guard. Сначала реальные короткие потребители, затем длинные.
3. Пилот: контрагент + номенклатура + размер ковра + отсутствие. Проверить создание/ошибку/отмену до массового переноса.
4. Кандидат/задача/оборудование. Отдельно проверить выбор людей, каталог/единицу, вложения и сохранение после ошибки.
5. Объект/заказ/сотрудник с полным набором существующих полей. Отдельные проверки скрытых разделов и payload; не терять поля при переносе.
6. Общий проход реестров и рабочих экранов: кандидаты, задачи, объекты, разовые, табель, согласования, планы, ковры, пустые состояния; календарные панели и имена.
7. Финальная сквозная проверка всех точек открытия и маршрутов, независимое ревью; только затем решать о закрытии UI-пакета/R0.

Общие компоненты должны иметь одного владельца на время правок. В параллельных задачах разделять потребителей, а не разрешать двум агентам одновременно менять Dialog/Popover. Сборки/тесты выполнять последовательно из-за недавнего OOM; не использовать общий `.next` одновременно для dev и production build.

## Рабочая группа и установки моделей

Зафиксировано 2026-10-31 по запросу заказчика. Это план распределения, не журнал запущенных агентов. Роли ниже не означают одновременный запуск всех исполнителей.

| Роль | Модель / reasoning effort | Задача и результат |
|---|---|---|
| Координатор | GPT-6.1 Sol / medium | Разбирает требования и короткие отчёты Luna, принимает решения по структуре, границам и приёмке. Не заменяет Luna в поиске по коду и реализации. Основной чат выбирается пользователем; модель основного чата автоматически не переключается |
| A — разведка и общая основа | GPT-6 Luna / medium | Сначала read-only карта форм, точек открытия, всех полей/defaults/payload, проверок и зависимостей. После разбора Sol — единственный владелец Dialog/Form layout, размещения меню, общих представлений людей/дат, dirty guard и навигации `/new`. Сначала реальные пилотные потребители. Сдаёт контракт компонентов, патчи и целевые тесты |
| B — короткие и средние формы | GPT-6 Luna / medium | Контрагент, номенклатура, размер ковра, отсутствие, замещение, кандидат, задача, тип/единица оборудования. Владеет user-absences и его календарной панелью. Использует готовую основу A; не переписывает shared-компоненты. Сверяет каждое поле и API-поведение с исходным состоянием |
| C — длинные формы | GPT-6 Luna / medium | Объект, разовый заказ/копия, сотрудник: секции, ошибки скрытых разделов, условные поля, сохранение draft между разделами, прежние capabilities и payload. Не упрощает бизнес-форму и не расширяет права |
| D — утверждённый проход рабочих экранов | GPT-6 Luna / medium | Реестры кандидатов/задач/объектов/заказов, имена и даты в табеле/календарях, вторичные кнопки, пустые состояния. Работает после освобождения затронутых файлов B/C. Не меняет формы, которыми ещё владеет другой агент |
| E — проверка | GPT-6 Luna / medium | Отдельная проверяющая роль без реализации: сверка состава полей и запросов, целевые тесты, сценарии и screenshots. Единый оператор браузера; не кликает в одной вкладке параллельно с координатором. Отчёт PASS/FAIL/NOT CHECKED с доказательствами; исправления возвращает владельцу |
| Независимый финальный ревьюер | GPT-6.1 Terra / high | Один целевой read-only проход по интегрированным изменениям: route-aware окна, Back/Forward/refresh, вложенные overlay, потеря ввода, повторные отправки, скрытые разделы и сохранение ACL. Не повторяет полный поиск по репозиторию и не реализует параллельную альтернативу |

### Очерёдность и ограничения

1. A составляет карту → Sol принимает точный контракт. Подготовка не повторяет полный аудит репозитория: только формы и затронутые общие компоненты.
2. A делает общую основу → B переносит пилотные короткие формы → проверяется пилот. До стабилизации основы массовый перенос не начинается.
3. B завершает оставшиеся короткие/средние формы; C параллельно работает с длинными, только после фиксации API shared-компонентов. Максимум два активных субагента, непересекающиеся наборы записываемых файлов.
4. D выполняет общий проход освобождённых рабочих экранов. A при необходимости решает интеграционные проблемы shared; один файл — один владелец. Календарь отсутствий не редактируют одновременно B и D.
5. E проводит проверку; владельцы исправляют конкретные дефекты. Terra выполняет один независимый проход. После исправлений повторяются затронутые проверки, а не весь цикл разведки заново.
6. Sol оценивает результат по контракту; непроверенные пункты остаются открытыми. R0 не закрывается автоматически из-за готовности форм.

Всем исполнителям: сначала AGENTS.md и применимые продуктовые/UI-контракты; существующие токены, поля, иконки, подтверждения и права; никакого production, deploy, commit/push, очистки данных или перезапуска сервисов без отдельного задания. Backend-реализация не выделяется в самостоятельную задачу: текущий пакет UI-only. Обнаруженная необходимость менять API/идемпотентность приносится Sol отдельным вопросом.

Передача задачи: цель → разрешённые файлы → неизменяемая логика → приёмка → краткий отчёт «файлы / изменения / проверки / ограничения». Не передавать каждому агенту полную историю чата; давать этот контракт и конкретную миссию. Роли можно выполнять повторно используемыми агентами, не создавая отдельного исполнителя на каждую форму.

Модель и effort при запуске задаются явно: `gpt-6-luna` / `medium`, для ревью `gpt-6.1-terra` / `high`. Эти overrides доступны в текущем инструменте; перед реальным запуском проверить фактическую доступность. Не заменять недоступную модель молча. `high/xhigh/max/ultra` для обычных переносов не использовать; усиление — только для конкретного затруднения с объяснением заказчику.

Навыки: A — проверка архитектуры/геометрии shared; B/C/D — выборочный Impeccable polish в пределах утверждённой работы; E — Impeccable audit и актуальные web-design-guidelines; Terra — независимое ревью рисков. Каждый исполнитель сам читает применимые инструкции навыка. Навыки не подменяют браузерную приёмку. Сборки/тесты — по очереди, без общей `.next` одновременно для build/dev. Более дорогая модель не заменяет управление памятью Docker.

Документация выбора model/effort: https://learn.chatgpt.com/docs/agent-configuration/subagents . Процент недельного лимита заранее не вычисляется: нет надёжного измерителя доступной квоты и полного будущего объёма. Экономия достигается узкими заданиями, краткими отчётами, повторным использованием агентов и одним финальным ревью, а не обещанным процентом.

## Приёмка — обязательная для каждой формы

- [ ] Все прежние поля, defaults, ограничения и разрешённые значения сверены с исходником и payload; нет потерянных/новых обязательных полей.
- [ ] Открытие из реестра, глобального «+», контекстной карточки; прямая ссылка, refresh, Back/Forward и закрытие имеют определённый результат.
- [ ] Фон сохраняет фильтры/scroll; пользователь не редактирует фон сквозь окно.
- [ ] Пустая и заполненная формы; короткие и максимально допустимые длинные значения; много выбранных людей/телефонов/пунктов.
- [ ] Кнопки окна видимы, нет горизонтального скролла; 390/768/1280 px и фактический zoom 200%, в том числе длинные подписи.
- [ ] Даты, select и меню у каждого края, после прокрутки/изменения размера; внутри Dialog/подтверждения не обрезаны и не скрыты слоями.
- [ ] Tab/Shift+Tab, Escape, возврат фокуса, Enter и textarea; лишняя отправка формы не происходит.
- [ ] Отмена/крестик/Escape с грязным вводом; отмена подтверждения возвращает ровно те же значения и выбранный раздел.
- [ ] Ошибка клиента и API, отказ в доступе/истёкшая сессия; введённое не уничтожается неожиданно, чувствительные поля не раскрываются другой роли.
- [ ] Ошибка в скрытом разделе делает его видимым и фокусирует поле; ошибка не сообщается одним только disabled-состоянием кнопки.
- [ ] Pending и повторный клик; успешное создание отделено от ошибки обновления реестра; неизвестный итог запроса не выдаётся за неуспех без оговорки.
- [ ] Реальный сценарий в изолированной локальной проверке, не только HTTP 200/typecheck; отсутствие повторных/лишних записей.
- [ ] Различия прав руководящего круга/менеджера и Employee/User сохранены; сокрытие поля не заменяет серверную защиту.
- [ ] Снимки до/после при одинаковых ширине, данных и состоянии; журнал реально выполненных и недоступных проверок.

Навыки: Impeccable audit/polish и актуальные web-design-guidelines помогают найти отклонения; они не заменяют сценарии, измерения и скриншоты. Без фактической проверки не ставить PASS. Установка новых UI-библиотек, изменение продакшена и публикация не входят в этот пакет.
