# План дня, календарь и табель — согласованный проход

Baseline: `42c7166fcc932bad11d5441d28db3b91a7344501`. Пользователь подтвердил порядок A → решения main → B/C → D → browser main → Terra → адресная перепроверка.

## Объём и владельцы

- A / Luna high: read-only обследование завершено. Отдельный раздел Reports не включён: скриншот показывает `/visit-plans` с собственным дневным отчётом.
- B / Luna high: `/visit-plans` и `/user-absences`, их page/CSS и scoped helper/tests.
- C / Sol high: `/timesheet`, grid/overview/cell-editing и entity styles/helpers/tests.
- D / Luna high: независимые тесты, типы, lint и изолированная сборка последовательно.
- Main: решения, документация, интеграция и единственный browser operator.
- Terra high: одно итоговое независимое source review.
- Одновременно не более двух помощников; один владелец файла. Shared/global изменения требуют отдельной передачи владельцу. Новая карта кодовой базы не нужна.

## Критерии

1. План дня: компактная дата с навигацией ±день/сегодня и подписанной иконкой обновления; пустое состояние без двойной карточки; создание только по существующему `canManage`; выбранный менеджер и день, редакторы, версии, отчёт и audit сохраняются.
2. Календарь Users: убрать только визуальный дублирующий заголовок, оставить доступное название; выровнять период/фильтры/create; целые группы переносятся без clipping. Сохранить существующий modal-create, фильтры и персональные права, не раскрывать приватные причины. Sticky identity/date, мягкая подсветка сегодня, текстовая легенда доступных типов.
3. Табель Employees: сохранить operational matrix, горизонтальный scroll и существующий correction flow. Закреплённые identity/date, читаемые ФИО, дни недели/выходные/сегодня, выбранная строка/столбец, стабильные границы. Компактная навигация, overflow hint только при необходимости.
4. Нажатие ячейки сначала объясняет доступные значения и факт; ручная корректировка остаётся отдельным явно разрешённым действием с существующей причиной/версией/audit. Никаких N+1 или новых данных/API.
5. Сводка и Excel имеют текущие одинаковые фильтры периода/объекта/сотрудника. Текст отличает начисления от выплат; расчёт и формат workbook не меняются.
6. Проверки загруженных UI на 390/768/1280/1600, длинные имена, меню у границ, прокрутка/выбор ячеек/клавиатура. Реальный zoom200% и физический touch не подменять resize. Неисполненные сценарии отмечать отдельно.

## Финансовая граница и найденное противоречие

`—` в текущем табеле означает `finalValue === 0`, а не отсутствие записи. Backend заполняет все дни; `hasFact` отдельно отражает attendance. Показывать нулевую сумму и источник в деталях, не обозначать её неизвестной и не создавать факт при просмотре.

Документ product-contract содержит позднее уточнение 2026-10-30 о делении месячного итога пополам и более ранний §5 о суммах дней 1–15/16–конец. Текущий runtime использует последний вариант. Это противоречие не разрешается UI-проходом: **никакие формулы, сохранённые суммы или права не меняются**. Не выдавать текущую формулу за вновь подтверждённое бизнес-решение. Сверку вынести отдельно после этого прохода.

## Ограничения

UI-only: без изменений backend/API/DTO/ACL/schema и lifecycle. User calendar не Employee availability; план не attendance; начисление не выплата. Без новых зависимостей, uploads, денежных операций, делегирования прав или очистки данных. Новые тестовые записи не создавать без конкретной необходимости и согласованного сценария. Git snapshot не backup БД/файлов. Закрывать только подтверждённые критерии.
