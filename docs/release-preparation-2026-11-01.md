## Перед выкладкой — обязательный preflight

1. Получить отдельное разрешение на работу с сервером. Проверить целевой host/project, фактические deployed SHA и image IDs, чистоту серверного checkout, compose overrides, здоровье и свободные RAM/диск. Не угадывать адреса и пути из примеров.
2. Проверить успешный полный CI итогового PR и отсутствие новых коммитов после проверки. Сохранить SHA, ссылку CI, версии инструментов и checksum пакета в операционный журнал.
3. Зафиксировать текущие image IDs и отдельные rollback-теги backend/frontend. Не удалять старые образы, volumes или прежние копии ради места без отдельного решения.
4. Сохранить закрытым способом PostgreSQL custom-format dump, globals, runtime-конфигурацию/ключи и согласованную копию MinIO с проверяемой связью с БД. Для согласованной точки остановить записи приложения и фоновых обработчиков либо использовать утверждённый механизм согласованного снимка. Git не является резервной копией данных или файлов.
5. Проверить права копий, SHA-256 и оглавление dump. Настоящее восстановление выполнить в отдельную временную БД, не поверх production. На копии применить именно эти шесть миграций, проверить статусы и основные чтения; результат записать. Файловую копию проверить на читаемость и соответствие ссылкам. Копии/секреты не загружать в Git или этот отчёт.
6. Проверить действующие production env и build-time `NEXT_PUBLIC_API_URL=https://<подтверждённый-домен>/api/v1`. Не копировать localhost/тестовые JWT/пароли из CI. Проверить ресурсы для LibreOffice и обработки PDF; новый PDF.js worker поставляется локально из сборки, не через внешний просмотрщик.
7. До запуска нового backend проверить ожидающие публикации и согласовать возобновление их доставки. `ObjectDailyReportPublicationService.onModuleInit()` запускает `flush()` сразу, затем каждые 15 секунд: в этой версии нет подтверждённого флага паузы. Закрытие пользовательского входа не останавливает worker. Если доставка до завершения smoke недопустима, **backend не запускать**: нужен отдельно реализованный и проверенный механизм удержания worker. Не удалять outbox и не помечать ожидающие записи доставленными ради выкладки.

## Последовательность выкладки

1. Подготовить checkout точного SHA и собрать backend/frontend **последовательно**, пока прежняя версия обслуживает запросы. Использовать `infra/docker/prod.Dockerfile`, `docker-compose.prod.yml` и реальные проверенные серверные overrides. Сохранить новые образы отдельными release-тегами до замены контейнеров.
2. Установить окно обслуживания и остановить все источники записей в рамках подтверждённого проекта; перед миграциями получить финальную согласованную копию. Не останавливать посторонние проекты. Не менять TLS, DNS и базы ради сборочной ошибки.
3. Выполнить штатный tools-сервис `migrate` с новым backend-образом (`prisma migrate deploy`), проверить отсутствие failed/pending миграций. При ошибке остановиться: не использовать `migrate reset`, `migrate dev`, seed или ручное исправление migration history.
4. После допуска по пункту 7 preflight запустить новый backend. **Это уже возобновление фоновых записей и доставки, а не read-only запуск**; зафиксировать время и изменение очереди/созданные сообщения после финальной копии. Дождаться health и проверить логи/доступ к новым моделям. Затем новый frontend; проверить ожидаемые image IDs и отсутствие циклических перезапусков. Обновление frontend зависит от здорового backend согласно compose.
5. Провести smoke ниже при всё ещё закрытом пользовательском входе, затем открыть пользовательские записи и наблюдать ошибки, очереди доставки, память и дисковое место. Worker при этом уже работает; не выдавать период smoke за отсутствие изменений в БД. Зафиксировать реально выполненные действия и известные ограничения отдельно от этого плана.

Команды исполняются только после подстановки **проверенных** серверных путей/env/overrides. Этот документ намеренно не содержит готовой команды с production credentials или неподтверждённым host.

## Smoke после выкладки

- HTTPS, `/api/v1/health`, frontend, загрузка JS/CSS/локального PDF-worker; отсутствие 500 и необъяснимых рестартов.
- Вход существующего пользователя; неавторизованный запрос защищённых API остаётся 401, чужой scope не раскрывается.
- Контрагенты: обзор/история/фильтры; связанные объекты, длинные имена и меню.
- Разовые: реестр/быстрый просмотр/полная карточка; ТЗ и каталог, доступ назначенного менеджера; сводка цикла без изменения денег. Не создавать реальные поступления ради smoke.
- Окна создания: открыть/закрыть, dirty-confirmation на тестовом черновике, поля/ошибки/даты; не сохранять фиктивные рабочие записи.
- Файлы: разрешённые фото/PDF/XLSX (XLSX — PDF-представление, не редактор книги), скачивание оригинала, понятный fallback неподдерживаемого формата. Не отправлять документы внешним viewer/CDN.
- План/календарь/табель: выбранная дата/месяц, прокрутка, длинные ФИО, read-only деталь, клавиатура и явный вход в корректировку по правам. Отдельный согласованный сценарий сохранения финансовой записи — не часть безопасного read-only smoke.
- Ежедневные отчёты и история исправлений/публикаций читаются; успешная доставка не предполагается по одному HTTP 200 страницы.
- Проверить как минимум узкий и широкий viewport; реальные данные и разные роли проверять только в разрешённом scope.

## Откат

При ошибке приложения закрыть пользовательские записи, остановить backend/worker и сохранить диагностику, включая доставки после первого старта. Уже видимые пользователям сообщения нельзя считать отменёнными остановкой контейнера; восстановление БД может вернуть outbox в состояние до доставки и потребовать отдельной сверки, чтобы не повторить публикации. Вернуть **совместимую пару** прежних образов, предварительно оценив совместимость старого кода с новой аддитивной схемой и уже созданными записями. Запуск прежнего backend тоже может возобновить worker. Не откатывать БД автоматически: добавленные данные нового релиза могут быть потеряны. Если требуется restore, согласовать потерю записей после точки копии и последствия уже выполненных доставок; восстановить согласованно PostgreSQL и MinIO в окне обслуживания, сначала проверив восстановление отдельно. Не удалять миграции и не применять обратный SQL без отдельного плана.
